# 第3章 ブロック②: IaCの考え方とTerraformハンズオン

## このブロックの範囲

- インフラは「触るもの」から「定義するもの」へ（IaCという考え方 / 変化を前提にしたインフラ / あるべき姿を記述する）
- コラム: 全部をIaC化しないという選択
- 手順書からコード管理へ（手順書の限界 / 構成ドリフト / 状態を管理するという転換）
- 最小構成でIaC体験（構成全体像 / Terraform定義 / init→plan→apply→destroy）
- コラム: AIを使ったインフラ構成の読み解き

ブロック①で IaC の思想面はかなり触れたので、このブロックは **「実際に手を動かしたときの感覚」と「IaCの留保（IaC化しない選択）」** を中心に対話する。

## セクション概要

- **宣言的（Declarative）アプローチ**: 操作手順を書くのではなく、「最終的にどのような状態であるべきか」を示す。これがIaCの特徴（p.39）。
- **構成ドリフト**: APIで容易に変更できることが、ばらつきを生む。「最初は小さな差にすぎないが、変更が積み重なるにつれて違いが見えにくくなる」（p.40, 図2）。
- **状態を管理するという転換**: コードとして残れば差分として確認・レビューできる。Gitで管理すれば誰がいつ何を変えたかも追跡可能。
- **最小構成のハンズオン**（図3, リスト1）: AWS上にVPC(10.0.0.0/16) + Public Subnet + IGW + EC2(t3.micro) + Session Manager用IAMロールをTerraformで構築。
- **基本操作の一周**: `terraform init` → `plan`（差分確認） → `apply`（適用） → `destroy`（破棄）。stateファイルが「定義と環境の橋渡し」をしている。
- **コラム「全部をIaC化しないという選択」**: 設計力・レビュー体制・バージョン管理の前提が必要。一時的な調査作業など、管理画面で操作する方が効率的な場面もある。あらかじめ線引きしておくことが無理のないIaC運用につながる。

## 自分の理解

- Terraform は今のプロジェクトでも現役で触っていて、ハンズオン部分（init/plan/apply/destroy、リスト1のコード）は体に染みている内容。
- p.39 コラム「**全部をIaC化しないという選択**」は、現役ユーザーの方が解像度が高い領域。
- 自分のIaC化「しない」基準は明確：
  - **コンソール上から連携した情報が必要なリソース**（一度しか表示されないトークン、外部連携で console UI 経由じゃないと拾えない情報）
  - **コンソールの何かのステップでチェック機構が必要なやつ**（ドメイン所有者確認、メール認証、利用規約同意など、人間の介在がライフサイクルに織り込まれている）

## 気づき・学び

- 自分の線引きは、組織都合で引いてる線というより **「プロバイダ側がIaC化を許してくれない領域」** に近い。「**操作の境界**」じゃなくて「**情報の境界**」を引いている、と言い換えられる。
- ただし「IaC化しない」と言っても、それらを完全に Terraform の外に置くわけではない:
  - **コンソールで有効化したリソースを `data` ソースとして Terraform に引き込む**
  - これにより、配下のリソースは普通にIaCで管理できる
  - リスト1の `data "aws_ami" "al2023"` と同じ思想。AMIは AWS が公開してる外部リソースで自分で `resource` として定義できないが、`data` で読み込めば downstream は IaC で管理できる
- このパターンは章の主張と矛盾せず、むしろ **より忠実**：
  > IaCの本質は、操作を自動化することではなく、〔…〕状態を管理することです（p.40）
  - 「状態を管理する」を素直にやってる
- 残された手作業（コンソールでの初期有効化）の手順は、**Terraform コード内のコメントに残す**ことが多い:
  - 手順がコードと同じ場所にある → リポジトリだけ見れば再現条件が分かる
  - データブロックの直前に「# 事前にコンソールで有効化が必要」的なコメントを添える
  - README と違ってドキュメントとコードのドリフトが起きない

## 実践への接続

- 現プロジェクトの IaC 線引きは、上記「情報の境界」+ data ソースパターン + コードコメントで運用中。
- p.43 コラム「**AIを使ったインフラ構成の読み解き**」は今はやっていないが、興味あり：
  - IaCコードレビューはAIが得意な領域（宣言的で文脈が線形、考慮漏れチェックリストが組織的に蓄積しやすい、セキュリティ観点も型化できる）
  - **「IaC構成レビュー支援」スキルの候補としてバックログに残す**

## 著者の主張のキャプチャ

> IaCは強力なアプローチですが、すべてをコード化すればよいという単純な話ではありません。〔…〕一時的な設定変更や、限定的な調査作業など、管理画面での操作の方が効率的な場面も存在します。何をコードで管理し、何を例外として扱うのか。あらかじめ線引きをしておくことが、無理のないIaC運用につながります。 — p.39 コラム

> IaCの本質は、操作を自動化することではありません。インフラをコードとして扱い、「どのような状態であるべきか」を明示し、その変化を管理することです。 — p.40
