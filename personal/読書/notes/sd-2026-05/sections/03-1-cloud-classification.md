# 第3章 ブロック①: クラウドの分類とパラダイムシフト

## このブロックの範囲

- 「はじめに」
- 「クラウドサービスの分類と特徴」: IaaS / PaaS / SaaS / サーバーレス型アーキテクチャ
- 「クラウド時代のITインフラの扱い方」: 物理的に触る → APIで操作する / 設計の自由度 / 構成の把握

## セクション概要

- クラウドサービスはNIST定義の3モデル（IaaS/PaaS/SaaS）で整理されてきた。サーバーレスはNIST外だが近年の代表モデル。
- 違いは機能ではなく「**どこまでを事業者が担い、どこからを利用者が担うのか**」という責任の境界（責任共有モデル、表1）。
- クラウドへの移行で、インフラは「物理的に触るもの」から「APIで操作するもの」に変わった。これにより：
  - 設計の自由度が上がり、構成パターンが多様化（差異が生まれやすくなる）
  - オンプレでは作業申請等が変更を抑制し記録が残りやすかったが、クラウドではAPIで即座に変更可能で意図と判断過程は自動記録されない
  - その解決策の一つがIaC（次ブロック）

## 自分の理解

- 一番響いたのは「**触るものから定義するものへ**」というフレーズ。章の中で象徴的なメッセージ。
- 章中には実は2段階の転換が並んでいる:
  - p.38 上段「物理的に触るインフラから **APIで操作する** インフラへ」（クラウド全般）
  - p.38 下段「インフラは『触るもの』から **『定義するもの』** へ」（IaC）
- この2つを **エンジニアリング的な飛躍** と **運用的な飛躍** に分けて捉えると腹落ちする:
  - 物理 → APIで叩ける = エンジニアリング的な飛躍（できることが変わった）
  - APIで叩ける → Terraformで構造化して定義 = **運用的な飛躍**（管理の仕方が変わった）
- 著者は両方をまとめて「パラダイムシフト」と書いているが、運用面では後者の方が大きい。

## 気づき・学び

- 「APIで叩けるだけ」だと、本文 p.38 のとおり「変更は個人の操作の中で完結してしまう」状態。
  IaC で構造化して初めて、誰でも再現可能・追跡可能な世界に変わる。
- IaC 化することで運用面で得られる嬉しさは大きく2つ:
  1. **チームで運用できる** — 「秘伝のタレ」を抜け出して、誰がいつ何を変えたか差分で見える化される（Git管理）
  2. **べき等性を持って管理できる** — 何度適用しても同じ状態に収束する。これが状態管理の核
- これは著者が p.40 で言う「IaCの本質は操作を自動化することではなく、状態を管理すること」に独立に辿り着いた形。

## 実践への接続

- 「秘伝のタレ」「特定のサーバーだけ設定が異なる」「緊急対応の修正が残ってる」（p.40の例）は、自分の経験的にも「全然ある」。
  環境差の問題はエンジニア共通の痛み。
- 個別の具体エピソードはぱっと出てこなかったが、構成ドリフトの実感はある。

## 残った疑問

- 特になし（IaaS/PaaS/SaaS/サーバーレス の責任分担モデルは深追いせず、概念パートとしては腑に落ちた状態でブロック②へ）

## 著者の主張のキャプチャ

> 抽象化は設計を不要にするものではなく、設計する場所を変えるしくみです。どこまでを自ら設計し、どこを委ねるのか。その境界を意識することが、サービスモデルを選ぶうえでのポイントになります。 — p.37

> 重要なのは、その都度の操作を追うことではなく、環境全体をどの方向に更新していくのかという視点です。 — p.39
