# 第3章 ブロック③: IaCの広がり

## このブロックの範囲

- IaCのアプローチは1つではない
- 宣言か命令か（Terraform/CFn vs AWS CDK/Pulumi）
- レイヤーの違いと組み合わせ（Terraform/CFn vs Ansible）
- 統制と抽象化というレイヤー（Policy as Code, Platform Engineering）
- ツールと考え方の関係（OpenTofu, IaCは目的ではなく手段）

## セクション概要

- IaCのアプローチは複数ある:
  - **宣言的（Declarative）**: 最終的にどのような状態であるべきかを記述。Terraform / AWS CloudFormation
  - **命令的（Imperative）**: どの順番で何を実行するかを記述。AWS CDK / Pulumi（プログラミング言語で記述）
- レイヤーも違う:
  - **インフラの構造を扱う**: Terraform / CloudFormation（VPC、サブネット、インスタンスなど）
  - **サーバー内部の状態を扱う**: Ansible（パッケージ、設定ファイル、サービス起動状態）
  - 組み合わせて使われることも多い
- IaCの考え方は、リソース定義にとどまらず広がっている:
  - **Policy as Code**: アクセス制御やリソースへのタグ付けルールをコードとして定義（AWS SCP, OPA）
  - **Platform Engineering**: チームや組織が再利用できる基盤そのものを設計・提供するアプローチ
- ツールはOpenTofuのフォーク事例など変わり続ける。重要なのはツールではなく、**「コードとして定義し、定義を基準に管理する」という考え方そのもの**。
- **「IaCは目的ではなく、そのための手段です」** — 章の締めくくり

## 自分の理解

- **宣言的 vs 命令的**: Pulumi/CDK は触ったことない。興味はゼロではないが、「Terraform より圧倒的な優位性があるとは思っていない」ので使っていない。
  - これは章のオチ「重要なのはツールではなく考え方」と完全に整合する態度。
  - Terraform のループや条件分岐が窮屈に感じることは「なくはない」が、`for_each` / `dynamic` / `optional()` 等で年々表現力が上がっており、致命的ではない。
- **Platform Engineering**: 成熟した PE 環境で働いた経験はない。今のプロジェクトは「各チームそれぞれ Terraform を書く」のがチームルール。ただし将来的にはやった方がいいと考えている。
- **共通化の判断軸**: 何を共通化するかについては、はっきりした基準がある:
  - 共通化していいもの: VPC、IAM ロール、モニタリング基盤 — 「エンジニアリングの本質ではない」undifferentiated heavy lifting
  - チームに任せるべきもの: アプリのデプロイ基盤 — 「アプリによって違う」ので共通化の優先度が低い
  - これは PE の王道：**undifferentiated heavy lifting** はプラットフォーム化、差別化要素はチームに残す

## 気づき・学び

- 章の中で「**境界を意識する／線引きする**」というモチーフが3段階で繰り返されている:
  | 場面 | 何を線引きするか |
  |---|---|
  | p.37 サービスモデル選択 | 「どこまでを自ら設計し、どこを委ねるのか」（IaaS/PaaS/SaaS/サーバーレス） |
  | p.39 コラム | 「何をコードで管理し、何を例外として扱うのか」（全部をIaC化しない選択） |
  | p.44 Platform Engineering | 「何を共通化し、何をチームに任せるのか」（PEの境界） |
  
  スケールが違うだけで、全部「境界を意識する」という同じ問いの繰り返し。
- 自分が今日の対話で繰り返し示していた「情報の境界」「本質ではない部分」「差別化されない部分」という判断軸は、章のメタテーマと響き合っている。

## 実践への接続

- 章全体を通しての一番の学び: **「Platform Engineering、やらなきゃだめだよね」**
  - 教科書的なIaCのまとめではなく、自分の現場に対する判断としての持ち帰り
- ラフプランの骨格はもう対話の中で組まれている:
  - 現状認識: 「各チームが Terraform を書く」
  - 整理済みの構図: 「VPC/IAM/モニタリングは共通化、デプロイは個別」
  - マインドシェア: 「将来的にはやった方がいい」
- 次のアクション候補:
  - 共通モジュールのスコープ定義
  - 社内向け IaC ドキュメント（Wikiレベルでも）
  - ゴールデンパスの最小版（VPC + IAM + モニタリングの基本セット）
